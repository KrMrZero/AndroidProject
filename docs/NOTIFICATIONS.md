# Уведомления: как устроены и что осталось

Документ описывает in-app уведомления CoFlow: коллекцию, репозиторий, экран,
колокольчик и места, где создаются события.

Реализован **вариант А**: уведомление создаёт клиент после успешного действия.
Cloud Functions не используются — они требуют платного плана Firebase.

## Как это работает

```
действие пользователя
        │
        ▼
ViewModel после успешного сохранения
вызывает NotificationRepository
        │
        ▼
Firestore: notifications/{id}   ← один документ на одного получателя
        │
        ▼  snapshot listener
NotificationRepository.observeByUserId(uid)
        │
        ▼
NotificationsViewModel (один экземпляр на приложение, создаётся в MainActivity)
        ├── список → NotificationsScreen
        └── unreadCount → NotificationBell(hasUnread)
```

Ключевая мысль: уведомление — это **сохранённый документ**, а не событие в UI.
Поэтому оно переживает перезапуск, хранит прочитанность и не зависит от того,
открыт ли экран в момент события.

## Модель данных

Коллекция `notifications`. Один документ — один получатель.
Если задачу назначили трём исполнителям, будет три документа.

| Поле | Тип | Назначение |
|---|---|---|
| `userId` | String | кому адресовано; по нему строятся запросы и правила |
| `type` | String | код типа (`task_assigned`, `task_taken`, ...) |
| `title` | String | короткий заголовок |
| `message` | String | текст уведомления |
| `projectId` | String | проект, к которому относится событие |
| `projectName` | String | название проекта на момент события |
| `entityId` | String | ID задачи или проекта — цель перехода |
| `actorId` | String | кто совершил действие |
| `actorName` | String | имя автора действия на момент события |
| `isRead` | Boolean | прочитано или нет |
| `createdAt` | Timestamp | время создания (UTC), сортировка «новые сверху» |

Пример:

```json
{
  "userId": "uid_maria",
  "type": "task_assigned",
  "title": "Вам назначили задачу",
  "message": "Иван назначил вам задачу «Подготовить отчёт»",
  "projectId": "proj_123",
  "projectName": "Диплом",
  "entityId": "task_456",
  "actorId": "uid_ivan",
  "actorName": "Иван И.",
  "isRead": false,
  "createdAt": "2026-11-17T10:15:00Z"
}
```

Типы (`NotificationType`):

| Код | Когда создаётся | Статус |
|---|---|---|
| `task_assigned` | назначили задачу | реализовано |
| `task_taken` | задачу автора взяли в работу | реализовано |
| `task_done` | задачу автора выполнили | реализовано |
| `added_to_project` | добавили в проект | не создаётся (см. ниже) |
| `project_updated` | изменился проект | нет |
| `role_changed` | изменилась роль в проекте | нет |
| `task_deadline` | скоро срок задачи | нет, нужен планировщик |

## API репозитория

```kotlin
create(dto): Result<NotificationModel>
createForUsers(userIds, dto): Result<Unit>   // по документу каждому, себя и дубли отбрасывает
observeByUserId(uid): Flow<Result<List<NotificationModel>>>
observeUnreadCount(uid): Flow<Int>
markAsRead(id): Result<Unit>
markAllAsRead(uid): Result<Unit>
deleteByUserId(uid): Result<Unit>            // при удалении аккаунта
```

`createForUsers` создаёт документы одной пачкой (`WriteBatch`): либо всем,
либо никому. Ошибка уведомления не отменяет основное действие — вызовы
обёрнуты в `runCatching`.

## Где создаются события

Сейчас уведомления создаются в двух местах:

| Событие | Файл / метод | Кому |
|---|---|---|
| Назначение задачи | `CreateTaskViewModel.onCreateTask` → `notifyAssignees()` | каждому исполнителю, кроме автора |
| Задачу взяли в работу | `TaskDetailScreenViewModel.onBottomActionClick` | автору задачи |
| Задачу выполнили | там же | автору задачи |

Важно:

- получатели берутся из выбранных исполнителей (`Assignees`), а не из строки
  `assigneeId` через запятую;
- себя уведомлять нельзя — проверка есть и в ViewModel, и в репозитории;
- задача, проект и имена сохраняются в уведомлении на момент события,
  поэтому старые уведомления не «ломаются» после переименований.

### Что пока не создаёт уведомления

- **Добавление в проект.** `AddProjectParticipantViewModel.onInviteClick` пока
  заглушка: он не сохраняет `memberships`, поэтому уведомлять не о чем.
  Когда приглашение начнёт реально писать в `memberships`, нужно добавить
  `ADDED_TO_PROJECT` и уведомить владельца проекта.
- **Смена роли.** `EditProjectViewModel` меняет роль через
  `membershipRepository.updateMember` — можно добавить `ROLE_CHANGED`.
- **Изменение задачи.** `EditTaskViewModel` пока сохраняет только название
  и описание, исполнители не меняются.
- **Удаление проекта/задачи.** Отдельного сценария удаления в UI нет.
- **Комментарии.** Их в проекте пока нет — тип уведомления не нужен.

## Экран и колокольчик

- Экран подписан на `observeByUserId(uid)`; после `markAsRead` Firestore сам
  присылает обновлённый список, ручная перезагрузка не нужна.
- `markAllAsRead` одним батчем помечает все непрочитанные.
- `hasUnread` считается по загруженному списку, поэтому пагинации пока нет:
  грузятся все уведомления пользователя.
- **Один экземпляр** `NotificationsViewModel` создаётся в `MainActivity` и
  передаётся в `NotificationsRoute`. Значение `hasUnread` уходит в колокольчики
  на «Мои задачи», «Проекты», «Профиль» и «Изменение профиля».
- При выходе из аккаунта и после удаления аккаунта вызывается
  `notificationsViewModel.reset()`, чтобы точка не осталась от прошлого пользователя.
- Колокольчик — общий `NotificationBell(hasUnread, onClick)` из `ui/components`.

### Внешний вид

Фронтенд просил убрать синий цвет:

- фон экрана — светлый, как в задачах и профиле (`coFlowTasksBackgroundBrush`);
- карточки — в тон фону (`Color(0xFFF2F6FF)`), без голубой заливки;
- непрочитанные отличаются жирным текстом и подписью «Не прочитано»;
- кнопка «Отметить прочитанным всё» — тёмный текст, а не белый.

## Правила Firestore

Файла правил в репозитории нет. Если будете подключать — не забудьте правила
для остальных коллекций, иначе `firebase deploy` закроет доступ к ним.

Минимальные правила для уведомлений:

```javascript
match /notifications/{id} {
  // Читать можно только свои
  allow read: if request.auth != null
              && resource.data.userId == request.auth.uid;

  // Создавать можно от своего имени
  allow create: if request.auth != null
                && request.resource.data.userId is string
                && request.resource.data.actorId == request.auth.uid;

  // Менять можно только isRead и только у своих
  allow update: if request.auth != null
                && resource.data.userId == request.auth.uid
                && request.resource.data.diff(resource.data)
                     .affectedKeys().hasOnly(['isRead']);

  // Удаление — только своих (нужно при удалении аккаунта)
  allow delete: if request.auth != null
                && resource.data.userId == request.auth.uid;
}
```

Системные уведомления (например, дедлайн) с пустым `actorId` по этим правилам
создать нельзя — для них понадобится Cloud Function с admin SDK.

## Индексы

Сейчас дополнительные индексы **не нужны**: запросы фильтруют только по
`userId` и `isRead` (равенство), а сортировка по времени выполняется на клиенте.

Если позже добавите пагинацию (`orderBy("createdAt")` + `limit`) или серверную
сортировку, понадобится составной индекс:

```
notifications: userId ASC, createdAt DESC
```

## Ограничения текущей версии

- нет перехода по клику на задачу/проект: клик только помечает прочитанным;
- нет пагинации и лимита — грузим все уведомления;
- нет дедлайнов и напоминаний;
- нет push (FCM) — только уведомления внутри приложения;
- клиентская запись: если приложение упадёт между действием и созданием
  уведомления, уведомление потеряется;
- старые уведомления не чистятся автоматически.

## Как проверить

1. Собрать: `./gradlew :app:compileDebugKotlin`.
2. Запустить приложение на двух аккаунтах (или эмуляторе + устройстве).
3. Аккаунт А создаёт задачу и назначает исполнителем аккаунт Б.
4. У аккаунта Б на колокольчике появляется точка, на экране уведомлений —
   запись «… назначил вам задачу …».
5. Аккаунт Б открывает задачу и нажимает «Взять задачу» — у аккаунта А
   появляется уведомление «… взял вашу задачу … в работу».
6. «Выполнить» — у автора появляется «… выполнил вашу задачу …».
7. «Отметить прочитанным всё» — точка гаснет, статусы меняются на «Прочитано».
8. Перезапустить приложение — уведомления и прочитанность остаются.

## Что дальше

1. Переход по клику: `type` + `entityId` → задача или проект.
2. Уведомления при добавлении в проект и смене роли.
3. Дедлайны: «ленивая» проверка при входе или WorkManager.
4. Пагинация и очистка старых уведомлений.
5. Push через FCM (отдельный этап: токены, разрешения, Cloud Function).
6. Правила Firestore и индексы — задеплоить вместе с остальными коллекциями.
